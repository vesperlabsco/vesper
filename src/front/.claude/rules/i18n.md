# i18n

## Stack runtime

- `react-i18next` + `i18next-browser-languagedetector`, initialisé dans `locales/i18n.ts`, exposé via `app/providers/I18nProvider.tsx` (monté dans `main.tsx`).
- Détection : `localStorage` en premier, sinon `navigator.language` (`load: 'languageOnly'` pour que `fr-FR`/`fr-CA` matchent `fr`). **Pas de segment d'URL** (`/en`, `/fr`) — la langue ne fait jamais partie du routing.
- Ressources bundlées statiquement (import JSON direct dans `i18n.ts`), pas de `http-backend` — seulement 2 langues, pas de justification à charger en réseau. À revoir si le nombre de langues/namespaces grossit significativement.
- Override par préférence de compte (**pas encore implémenté**, auth absente) : le point d'extension est un appel à `i18n.changeLanguage(user.preferredLanguage)` depuis le futur `AuthProvider` une fois le profil chargé — se re-persiste automatiquement en `localStorage` (pas de mécanisme dédié à écrire, le detector le fait déjà).

## Convention de fichiers

- Un namespace JSON par espace : `common`, `org-admin`, `clinic-admin`, `app` — dupliqué dans chaque dossier de langue (`en/`, `fr/`).
- Une clé de traduction utilisée dans l'espace `clinic-admin` va dans `clinic-admin.json`, pas dans `common.json`. `common.json` est réservé à ce qui est réellement partagé entre les 3 espaces (boutons génériques, messages d'erreur globaux, etc.).
- Ne jamais coder en dur du texte utilisateur dans un composant — toujours passer par la clé i18n, même pour du texte visiblement "temporaire". Fait respecter par le linter (`eslint-plugin-i18next`, règle `no-literal-string` — voir [[quality-checks.md]]), pas seulement à la revue.
- Ajouter une clé dans `fr/` implique de l'ajouter dans `en/` dans le même changement (pas de langue qui traîne en retard).

## Structure interne des fichiers JSON

- À l'intérieur d'un namespace, les clés sont **imbriquées par composant** : un premier niveau nommé exactement comme le composant React qui l'utilise (PascalCase, cohérent avec `naming.md`), puis les clés de ce composant. Un seul niveau d'imbrication (pas de pyramide `A.B.C.D`) — si un composant a besoin de plus de structure, c'est le signal qu'il doit être découpé.
  ```json
  {
    "Hero": {
      "getStarted": "Get started"
    }
  }
  ```
  Appel : `t('Hero.getStarted')`. i18next gère nativement le `.` comme séparateur, aucune config supplémentaire.
- Objectif : en éditant un composant, on sait immédiatement où trouver/ajouter ses clés — la structure JSON reflète l'arbre de composants plutôt qu'une taxonomie arbitraire.
- Corollaire : quand on modifie/supprime du texte dans un composant (ou qu'on supprime le composant), supprimer les clés correspondantes dans `en/` **et** `fr/` dans le même changement — pas de clé orpheline qui traîne parce que le composant qui la référençait a changé. Comme la structure est nestée par composant, une clé orpheline se repère facilement (le bloc à son nom n'est plus utilisé nulle part) — pas d'outillage automatique pour ça aujourd'hui, à la charge de la revue.
